# Rationale

This project uses a policy and claims tracker because it demonstrates protected REST APIs, related MongoDB collections, and end-to-end business workflows clearly. The API is organized around `/api/policies` and `/api/claims` resources with standard URLs and HTTP methods. `GET /api/policies` and `GET /api/claims` list records, `POST` creates new records, `PUT` updates existing records, and `DELETE` removes them. Claims also support `POST /api/claims/:id/notes` so the application can demonstrate a protected nested resource. Status codes are used consistently: `200` for successful reads and updates, `201` for creation, `204` for deletion, `400` for validation problems, `401` for missing authentication, and `404` when a record is missing.

The Express project is split into separate files for routes, middleware, and data because that keeps the code easier to test and maintain. The route files handle HTTP behavior, the middleware files handle request logging, authentication, and centralized error handling, and the data layer manages JSON persistence with `fs` and `path` or MongoDB persistence through shared connection helpers. Using `dotenv` keeps environment-specific settings out of the code. The JSON store remains available for simple fallback runs, while MongoDB is used for the main capstone demonstration.

Error handling focuses on bad input, missing authentication, and missing resources. If a policy or claim payload is invalid, the API returns `400`. If a bearer token is missing or expired, the API returns `401`. If a policy or claim cannot be found, it returns `404`. Unexpected failures go through centralized error middleware and return `500`. The API also supports query parameters for filtering policy and claim lists during the demo.

AI tools helped most with structure ideas, naming, and front-end layout suggestions. They were less reliable when they drifted away from the capstone scenario, so I reviewed and rewrote that content to fit a policy claims tracker. The main lesson was to use AI as a drafting tool, then validate behavior, match the rubric carefully, and remove anything that did not serve the final product.
